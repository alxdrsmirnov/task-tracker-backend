# Исследование DDD

Запусти учебную сессию стратегического анализа продукта по DDD.

## Вызов

```text
/ddd-discovery <описание бизнес-идеи, продукта или ТЗ>
```

## Перед началом

Полностью прочитай:

1. `docs/ddd/strategic-analysis-ddd.md` — авторитетный пятишаговый процесс;
2. `docs/ddd/strategic-ddd-learning.md` — формат учебного взаимодействия.

Не пересказывай пользователю эти документы.

Проверь существующие результаты:

```text
docs/ddd/strategic/domain-model.md
docs/ddd/strategic/business-scenarios.md
docs/ddd/strategic/domain-events.md
docs/ddd/strategic/subdomains.md
docs/ddd/strategic/bc/context-map.md
```

Продолжи с первого незавершённого шага. Отсутствующий файл означает, что подтверждённого результата шага пока нет. Новый анализ начинай только по явной просьбе; старые выводы при новом старте считаются материалом для проверки, а не истиной.

Если нет ни описания, ни результата для продолжения, задай один вопрос: попроси обычным языком описать продукт и решаемую проблему.

## Выполнение шага

Для каждого из пяти шагов:

1. Используй подтверждённые результаты предыдущих шагов, описание продукта и доступные источники.
2. Сначала предложи цельный черновик результата шага, не вытягивая его из пользователя длинной анкетой.
3. Кратко покажи основания и только существенные пробелы.
4. Предложи принять результат или указать исправления.
5. При коррекции сохрани согласованные части и замени отвергнутые выводы.
6. После явного подтверждения запиши результат в файл, указанный методикой.
7. Только затем переходи дальше.

Предварительный вопрос задавай лишь тогда, когда без ответа нельзя построить полезный черновик. Если можно продолжить с явно обозначенным предположением, сначала покажи черновик.

Если новое знание противоречит подтверждённому решению, покажи противоречие и задай один вопрос. Не выбирай версию самостоятельно.

Поведение эталонного продукта проверяй по актуальным первичным источникам, когда оно влияет на вывод. Всегда отделяй факт об эталоне от решения создаваемого продукта.

## Правила шагов

### Шаг 1. Домен и проблема

Сразу предложи описание деятельности, боли без продукта, полезного результата, границы продукта и начального словаря. Не создавай отдельный контракт исследования и не повторяй очевидную цель пайплайна.

### Шаг 2. Участники и бизнес-сценарии

Стремись к максимально широкому полезному покрытию:

- пройди всех значимых участников, области и жизненные циклы;
- включи основной поток, доступ, совместную работу, администрирование, автоматизации, отказы и исключения;
- каждый сценарий формулируй как `кто → цель → наблюдаемый результат`;
- добавляй сценарии, пока находятся новые цели, результаты, участники, варианты или исключения;
- не устанавливай квоту и не сокращай каталог ради компактности;
- не размножай один бизнесовый результат по кнопкам, экранам, API и обычным CRUD-операциям.

### Шаг 3. Доменные события и бизнес-правила

Для каждого принятого семейства сценариев покажи намерение, значимые события в прошедшем времени, причинный порядок, важные правила, реакции, альтернативы и открытые вопросы.

Не создавай технические события и не проектируй агрегаты, таблицы, транзакции, API, владельцев данных или структуру кода.

### Шаг 4. Субдомены

Группируй сценарии, события и правила по общей бизнесовой цели, языку, специализированному знанию и причинам изменений. Для каждого субдомена объясни назначение, состав, результат, отношения и классификацию `Core / Supporting / Generic`.

В рамках этого пайплайна выделяй ровно один `Core`-субдомен — единую область, в которой сосредоточена главная отличительная ценность продукта. Если несколько тесно связанных областей выглядят ключевыми, сначала представь их как внутренние бизнесовые способности одного `Core`, а не как несколько равноправных ядер. Это осознанное правило данного пайплайна, а не универсальный запрет DDD на несколько `Core`-субдоменов.

Не получай субдомены из повторяющихся существительных, экранов или CRUD-модулей. Не строй искусственную иерархию: вложенность нужна только при реальной декомпозиции бизнесовой области.

### Шаг 5. Ограниченные контексты и карта

Внутри одного шага:

1. предложи кандидатов в BC;
2. проверь их несколькими показательными цепочками событий из шага 3;
3. объедини, раздели или скорректируй слабые границы;
4. построй Context Map и объясни каждую связь.

В совокупности проверочные цепочки должны затронуть каждый кандидат в BC и каждую значимую связь. Не назначай направление зависимости там, где отношение действительно симметрично.

`Subdomain = BC` используй только как начальную гипотезу. Не создавай BC для каждой сущности и не подменяй карту контекстов схемой HTTP-вызовов.

## Запись и ограничения

Не записывай неподтверждённую модель и не копируй в документы весь диалог. Отсутствующий будущий файл не создавай пустым.

Стратегический анализ заканчивается проверенной Context Map. Агрегаты, сущности, объекты-значения, Prisma, API, NestJS-модули, структура каталогов и программный код относятся к отдельному тактическому процессу.

Во время команды не изменяй исходный код, Prisma schema, миграции, transport или инфраструктуру.

Mermaid используй только там, где схема действительно помогает. Context Map делай компактной, в несколько рядов, с короткими подписями и объяснением направления каждой связи.
