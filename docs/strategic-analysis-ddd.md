# Справочник: стратегический анализ по DDD

> Пошаговый процесс стратегического проектирования: от «есть идея продукта» до карты bounded contexts и плана детального моделирования. Переиспользуемый — подходит для любого проекта. Написан для начинающих: каждый шаг объяснён, обоснован и показан на примерах.
>
> Как пользоваться: иди по шагам сверху вниз. Не переходи дальше, пока не зафиксировал артефакт шага в docs проекта. Помни: на реальном проекте ты будешь прыгать между шагами назад-вперёд — это нормально, пайплайн снижает когнитивную нагрузку, а не закован в камень.

## Откуда этот процесс

Единого «официального» пайплайна стратегического DDD нет. Этот — синтез признанных источников, проверенный на реальном проекте:

- Vaughn Vernon, «Implementing Domain-Driven Design» (красная книга) — субдомены, core domain, контекстные карты (гл. 2–3, 13).
- Vlad Khononov, «Learning Domain-Driven Design» — эвристики классификации субдоменов.
- Eric Evans, «Domain-Driven Design» (синяя книга) + Model Exploration Whirlpool — гл. 14 и итеративное исследование модели.
- Alberto Brandolini, EventStorming — формат «команда → событие → политика».
- Business Capability Mapping — возможности глаголами как мост от бизнеса к контекстам.
- ddd-crew Starter Modelling Process — ближайший «канонический» аналог (8 шагов).

Соответствие наших шагов процессу ddd-crew:

| Наш шаг | ddd-crew | Что там |
| --- | --- | --- |
| 0–1 Рамка, понять домен | Understand | бизнес-модель, цели, пользователи |
| 2–3 Возможности, слипание | Discover + Decompose | EventStorming, capabilities, эвристики декомпозиции |
| 4 Классификация | Strategize | Core Domain Charts |
| 5–6 BC, карта контекстов | Connect + Define | Domain Message Flow, Bounded Context Canvas |
| 7–8 Набросок, итерации | Define + Code | Bounded Context Canvas, Aggregate Canvas |
| — (можно пропустить в соло) | Organise | проектирование команд под границы |

## Термины простыми словами

- **Домен** — деятельность, которую обслуживает продукт. Не код и не фичи. Пример: для Asana-подобного продукта домен — «координация совместной работы», а не «управление задачами» (это механика).
- **Субдомен** — область внутри деятельности со своими правилами и языком.
- **Bounded Context (BC)** — граница, внутри которой слова и правила означают одно и то же. «Статус» в контексте задачи и «статус» в контексте проекта — разные вещи, и граница позволяет им не путаться.
- **Инвариант** — правило, истинное после каждой операции («у задачи ровно один ответственный»).
- **Агрегат** — кусок модели, меняющийся атомарно, за одну транзакцию, чтобы инвариант не разъехался.
- **Upstream / downstream** — направление влияния: upstream поставляет факты, downstream адаптируется.
- **Integration event** — событие-факт для других контекстов с минимальным payload («аккаунт зарегистрирован: id»).
- **Core / Supporting / Generic** — классы субдоменов: главная дифференциация / специфично, но заменяемо / стандарт рынка.

## Пайплайн

```text
Шаг 0. Рамка и охват
Шаг 1. Понять домен (4 вопроса)
Шаг 2. Карта возможностей (глаголы)
Шаг 3. Слипание → кандидаты в субдомены
Шаг 4. Классификация core / supporting / generic
Шаг 5. Bounded contexts (карточки границ)
Шаг 6. Карта контекстов (связи и интеграции)
Шаг 7. Тактический набросок (кандидаты, не решения)
Шаг 8. Детальные итерации по каждому BC
```

Шаги 0–6 — стратегия. Шаг 7 — мостик. Шаг 8 — детальное моделирование.

Рекомендуемая структура артефактов в docs: один стратегический документ (шаги 0–7), карта контекстов со схемой, и по файлу на каждую итерацию BC (шаг 8).

## Шаг 0. Рамка и охват

**Цель.** Зафиксировать, что строим и — важнее — что сознательно НЕ строим.

**Почему это первый шаг.** Любой спор о границах («а должен ли трекер хранить файлы?») неразрешим без зафиксированного охвата: обе стороны по-своему правы. Список «не моделируем» превращает бесконечные споры в ссылку на документ. Это же защита от расползания scope — главной болезни пет-проектов.

**Как делать.**

1. Продукт одной строкой: «копия Asana (минимум + уведомления)», «маркетплейс handmade-товаров».
2. Список «моделируем» — возможности, которые войдут в продукт.
3. Список «не моделируем / anti-scope» — всё, о чём осознанно отказываемся сейчас. Anti-scope — это возможности, о которых решили «нет, даже если попросят».
4. Если есть эталонный продукт — зафиксируй: его поведение = решение по умолчанию, отклонения документируются.

**Пример рассуждения (кейс: клон Asana).**

> «Копируем Asana. Но Asana огромна: биллинг, вложения, поиск, автоматизации, отчётность, цели, портфели... Берём минимум + уведомления: задачи, проекты, секции, поля, комментарии, участники, My Tasks, Inbox. Всё остальное — в "не моделируется". Кастомные роли — anti-scope: Asana обходится фиксированным набором (admin/editor/commenter/viewer), нам хватит.»
>
> Отдача пришла позже: когда в обсуждении доступа возникла идея настраиваемых политик, ответ уже был записан — anti-scope, пока не появится реальный сценарий с capability-матрицей.

**Пример переноса (другой домен).** Интернет-магазин: «моделируем: каталог, корзину, заказы, оплату, доставку. Не моделируем: рекомендательный движок, программу лояльности, возвраты v2». Уже на этом шаге видно, где НЕ будет субдоменов.

**Артефакт:** раздел «Граница домена» в стратегическом документе.
**Типичная ошибка:** пропустить шаг — тогда каждый спор решается «а давайте добавим», и карта субдоменов растёт бесконечно.

## Шаг 1. Понять домен

**Цель.** Ответить «о чём это и для чего» — до любых сущностей, таблиц и классов.

**Почему это критично.** Субдомены выделяются из деятельности. Если домен понят через механику («управление задачами»), то и нарезка получится по механике («задачи», «проекты») — а это воспроизводит схему БД и рождает god-контексты. Домен у Вернона: «что организация делает и мир, в котором она это делает».

**Как делать — четыре вопроса, отвечай развёрнуто и обосновывай каждый ответ.**

1. **Что делают** — какая деятельность происходит в продукте? Ищи смысл, а не механику. Приём проверки: найди продукт с той же механикой, но другой деятельностью — если такой есть, ты описал механику, а не домен.
2. **Кто участники** — жизненные роли («постановщик работы», «исполнитель», «наблюдатель»), а не системные (`admin`, `user`). Из жизненных ролей позже рождаются сценарии; из системных — ничего.
3. **Какую боль снимает** — что ломается без продукта? Боль — это критерий проверки всех будущих решений: когда позже спросишь «должен ли проект знать о задачах?», ответ ищется через «что из боли ломается при каждом варианте».
4. **За что платят** — главная ценность vs «ожидается по умолчанию». Этот ответ — заготовка классификации core/supporting/generic на шаге 4.

**Пример рассуждения (кейс: клон Asana).**

> Вопрос 1: «Что делают компании в трекере? Создают задачи? Нет — это механика. По смыслу они координируют работу множества людей, чьи действия зависят друг от друга: маркетинг ждёт лендинг от разработки, разработка — тексты от маркетинга. Проверка приёмом: Todoist — та же механика ("списки задач"), но персональный органайзер, другая деятельность. Значит домен — координация совместной работы внутри компании».
>
> Вопрос 3 (боль): «Без инструмента: невидимость (состояние узнаётся расспросом, платим статус-встречами), размытая ответственность (задача в чате не имеет владельца), потеря контекста (обсуждение в мессенджере оторвано от работы) и конфликт процессов отделов (разработка — по колонкам, бухгалтерия — по месяцам)».
>
> Вопрос 4: «За что платят? Вход в аккаунт? Нет, ждут по умолчанию. Комментарии? Стандарт. А вот "одна задача живёт в нескольких проектах без копий" и "каждый отдел настраивает свой процесс" — за этим идут в Asana, а не в Trello. Не нарисовав ни одного субдомена, мы получили принцип классификации: платят → core, заменяемо → supporting, стандарт рынка → generic».

**Пример переноса (другой домен).** Интернет-магазин: деятельность — «превращение потребности покупателя в доставленный товар»; участники — покупатель, продавец, сборщик, курьер; боль — «не знаю, где мой заказ»; платят за ассортимент + предсказуемость доставки, а не за корзину (корзина — стандарт).

**Артефакт:** формулировка домена одним абзацем + ответы на 4 вопроса.
**Типичная ошибка:** формулировка через механику. От неё зависит, что станет ядром: «списки задач» → ядро список; «координация» → ядро то, что координирует людей.

## Шаг 2. Карта возможностей

**Цель.** Описать домен деятельностью, а не существительными. Субдомены — области деятельности, поэтому и материал для них — деятельность.

**Почему не существительные.** Если начать с Task/Project/Comment, ты просто перепишешь будущую схему БД. Существительные скрывают причины изменений: за словом «проект» живут две разные деятельности («раскладывать работу» и «настраивать процесс»), и только глаголы это вскрывают.

**Как делать.**

1. Выпиши 8–15 возможностей **глаголами деятельности**: «поручать работу», «настраивать процесс под отдел».
2. Правила отбора: возможность = *что*, не *как* (без технологий и UI); самостоятельна (имеет смысл без соседней); привязана к боли или роли из шага 1.
3. Проверка полноты: каждая боль и каждая роль покрыта хотя бы одной возможностью.

**Пример рассуждения (кейс: клон Asana).**

> «Поручать работу» — из боли «размытая ответственность» и роли постановщика. «Собирать личный фокус исполнителя» — из роли исполнителя (в Asana это My Tasks). «Держать людей в курсе изменений» — из боли «статус-встречи».
>
> Тонкое место: «организовывать работу в представления» и «настраивать процесс под отдел» — две возможности или одна («проекты»)? Смотрим на действия: раскладывать одни и те же задачи по-разному ≠ определять свои этапы и поля. Разные действия, разные цели — две возможности. Позже именно эта пара станет вторым дифференциатором продукта. Если бы мы работали существительными, «проект» проглотил бы обе — и различие потерялось.
>
> Анти-пример: «хранить файлы» в список не попало — это способ (*как*), а не деятельность (*что*).

**Пример переноса.** Интернет-магазин: «вести каталог», «оформлять заказ», «собирать заказ», «доставлять», «оповещать покупателя», «принимать оплату». Заметь: «принимать оплату» — возможность, хотя реализацией будет Stripe/ЮKassa — деятельность-то бизнесовая.

**Артефакт:** таблица «возможность → откуда взялась (боль/роль)».
**Типичная ошибка:** возможности-технологии («слать email») и возможности-дробинки («редактировать название задачи» — это часть «вести работу», а не отдельная возможность).

## Шаг 3. Слипание → кандидаты в субдомены

**Цель.** Сгруппировать возможности в области деятельности — это и есть кандидаты в субдомены.

**Как делать.** Группируй по трём признакам сцепления:

1. **Общий язык** — возможности говорят одними понятиями. Проверка: попробуй описать обе возможности одним абзацем — если слова не пересекаются, язык разный.
2. **Общая причина изменений** — если бизнес-правило меняется, сколько возможностей заденет? Меняющиеся вместе — вместе.
3. **Общая бизнес-цель** — служат одной цели из шага 1.

Правило скепсиса: **новая группа появляется только с доказанной причиной**. По умолчанию возможности живут вместе; разделяем при наличии аргумента, а не потому что «так аккуратнее».

Для спорных кандидатов — **три теста отдельности**:

- Есть свой язык, не состоящий из чужих слов?
- Есть своя бизнес-цель / причина изменений?
- Есть своё состояние с жизненным циклом?

Кандидат, проваливший все три — не субдомен, а механика внутри владеющих контекстов.

**Пример рассуждения (кейс: клон Asana), простое слипание.**

> «Поручать работу» + «вести по циклу» + «личный фокус» слипаются: язык общий (работа, ответственный, состояние), цель одна (у каждой работы есть ответственный и видимое состояние). «Организовывать в представления» + «настраивать процесс» — вторая группа: язык другой (разрез, этап, поле, группировка), причина изменений своя (эволюция представлений и кастомизации). Этот разрез — «исполнение vs организация» — позже лечит god-контекст.

**Пример рассуждения, спорный случай 1 — обсуждения.**

> «Обсуждать работу» — отдельная группа? Тест 1, язык: комментарий, упоминание — но это речь *о* работе, без неё не существует. Тест 2, причина изменений: все правила обсуждений — правила о работе (кто может комментировать, кого упоминание делает участником). Тест 3, состояние: своего нет. Вердикт: НЕ субдомен; живёт внутри «исполнения работы». И обязательно записываем триггер пересмотра: появятся модерация, треды, реакции, второй носитель комментариев — тесты пересдаются.

**Пример рассуждения, спорный случай 2 — доступ (с книжной ловушкой).**

> «Определять, кто что видит и может» — в книге Вернона есть отдельный IAM-контекст, почему нам нельзя? Смотрим в книгу точнее: у SaaSOvation вынесли идентичность и доступ *грубого* уровня — со своим языком (тенант, подписка), своим состоянием (подписки истекают) и своей бизнес-целью (IAM продавался отдельно). А права на доменные объекты («может ли этот человек редактировать backlog item») остались внутри core-контекста. Наш «доступ» говорит только чужими словами («editor проекта», «участник задачи»), состояния не имеет (роли — фиксированные enum'ы). Вердикт: политики внутри контекстов-владельцев. Триггер выделения: настраиваемые политики, временный доступ, аудит. Урок формы: книга — не каталог готовых границ, а набор тестов на отдельность.

**Пример переноса.** Интернет-магазин: «вести каталог» и «принимать оплату» не слипаются — разный язык (товар/категория vs платёж/транзакция/возврат), разные причины изменений (контент vs платёжные провайдеры). А «оповещать покупателя» — спорный случай по образцу уведомлений: свой язык (получатель, шаблон, доставка), своя причина (каналы), реагирует, а не управляет → отдельный кандидат.

**Артефакт:** таблица «кандидат → возможности → аргумент за отдельность» + триггеры пересмотра для невыделенных.
**Типичная ошибка:** резать по существительным; выделять механику без тестов отдельности; плодить кандидатов «для аккуратности» (каждый лишний субдомен — это интеграционный налог на всю жизнь проекта).

## Шаг 4. Классификация core / supporting / generic

**Цель.** Понять, где концентрировать качество модели. Ресурсы ограничены: core получает лучшие модели и тесты, generic — покупку или простейшую реализацию.

**Как делать.** Тест дифференциации для каждого кандидата:

- **Core** — за это платят, этим продукт отличается от конкурентов; ошибка модели = смерть продукта.
- **Supporting** — специфично для домена, но заменяемо (можно упростить/переписать/купить) без потери отличия; ошибка = баг.
- **Generic** — стандарт рынка, покупное решение (идентичность, платежи-эквайринг).

Приём проверки core: «этого нет у типового простого конкурента». Если у бесплатного аналога такое есть — это не core.

**Пример рассуждения (кейс: клон Asana).**

> «Исполнение работы»: «одна работа — много проектов без копий, один ответственный» — есть ли у Trello или блокнота? Нет. → Core?
> «Организация работы»: «каждый отдел настраивает свой процесс» — тоже нет. → Core?
> Получилось два core — стоп, это красный флаг (см. «Нюанс про число core» ниже). Проверка: продукт отличается этими частями *по отдельности* или это грани одного отличия? Asana выигрывает не задачами отдельно и не проектами отдельно, а тем, как они работают вместе. Дифференциация одна → один core-поддомен «координация работы». Разрез на два BC при этом остаётся — но это уже решение solution space (шаг 5), а не классификация.
> «Обсуждения»: комментарии и упоминания есть в любом трекере — не дифференциатор. Отдельный субдомен? Первая реакция — «нет, слишком мало логики». Стоп: размер — не критерий, критерий — отдельность проблемной области (своё состояние, свои инварианты). Пока обсуждения — только комментарии к задаче, своего состояния почти нет → можно держать в core-контексте. Но стоит в охват добавить лайки и ленту активности (хронику объекта, читающую события всей системы) — состояние и инварианты появляются (один лайк пользователя на объект; идемпотентность записи ленты по id исходного события) → отдельный supporting-субдомен Collaboration со своим BC. Два урока: тест дифференциации применяется к субдоменам, а не к каждой возможности (иначе из core испарятся и сами задачи — CRUD есть у всех); карту субдоменов пересматривают, когда растёт понимание домена, — это живой документ.
> «Структура компании»: нужно для B2B, но продукт этим не отличается. → Supporting.
> «Уведомления»: группировка Inbox специфична, но заменяема готовым notification-center. → Supporting.
> «Личность»: покупное целиком. → Generic.
>
> Обрати внимание на форму обоснований: каждое называет конкретный дифференциатор. «Core, потому что тут ключевая ценность» — тавтология, не обоснование.

**Пример переноса.** Интернет-магазин: core — то, чем он отличается (для одного это логистика «за 2 часа», для другого — рекомендации); supporting — каталог, заказы; generic — платёжный эквайринг, идентичность. Один и тот же субдомен в разных продуктах имеет разный класс: поиск — generic для блога и core для маркетплейса.

**Нюанс про число core.** Жёсткого числа в каноне нет, но дух дистилляции — один core на продукт: core — это то *одно*, ради чего продукт существует, куда идут лучшие модели и лучшие люди. Несколько core в одном продукте — не запрещено, но это красный флаг с двумя типичными диагнозами: (1) недожатая дистилляция — «если всё core, то ничто не core»; (2) технический разрез solution space (два BC с разными траекториями изменений) ошибочно поднят до классификации problem space. Проверочный вопрос: «продукт отличается от конкурентов этими частями *по отдельности* — или это грани одного отличия?» Во втором случае правильная формулировка: один core-поддомен, несколько BC внутри (поддомен — problem space, BC — solution space, соответствие не обязано быть 1:1). Множественные core легальны у компании с несколькими продуктами или линиями бизнеса — по одному на каждый.

**Артефакт:** таблица классификации с обоснованием + перекрёстная проверка (совпадает ли вывод «снизу» из возможностей с выводом «сверху» из ценности?).
**Типичная ошибка:** тавтологическая классификация; несколько core без проверки «это грани одного отличия?»; классификация по технической сложности вместо бизнес-дифференциации (сложность ≠ core: сложная supporting-механика остаётся supporting).

## Шаг 5. Bounded contexts

**Цель.** Наложить границы моделей на карту субдоменов. Субдомен — проблема (область деятельности), BC — решение (граница модели).

**Как делать.**

1. Рабочее выравнивание: один субдомен ≈ один BC. Это стартовая точка, не закон: бывает один субдомен → несколько BC и наоборот. Но каждое отклонение — осознанное решение с записанной причиной (почему нельзя 1:1). Два разнонаправленных отклонения в одной маленькой системе — одновременно «один субдомен → два BC» и «один BC → два субдомена» — почти всегда сложность ради сложности: выбери одно.
2. Карточка каждого BC: **назначение / владеет / не владеет / использует у других / предоставляет другим**. Самая ценная часть — «не владеет»: граница держится на отказах.
3. Валюта общения: какие идентификаторы и факты контекст публикует наружу, и на каком языке говорит downstream.

**Пример рассуждения (кейс: клон Asana).**

> Карточка Workspace: «Назначение — описать пространство, людей, отделы. Владеет: Workspace, membership, Team. НЕ владеет: ProjectId, TaskId, проектными ролями». Именно строка «не владеет» не даст потом притащить задачи внутрь Workspace «на минуточку».
>
> Валюта общения: downstream получает `WorkspaceMemberId`, а не `AccountId`. Почему? Identity знает человека, Workspace — его членство. Это паттерн из книги: AgilePM говорит о `TeamMember`, а не о пользователе IAM-контекста. Каждый контекст переводит чужие факты на свой язык, а не разделяет чужие сущности.

**Пример переноса.** Интернет-магазин: «Каталог» владеет товаром и ценой, «Заказы» — заказом и его статусом. Заказ ссылается на товар по `productId` + снимку названия/цены на момент покупки — а не на живую сущность каталога: цена в каталоге изменится, а в заказе обязана остаться исторической. Это и есть граница моделей.

**Артефакт:** раздел «Ограниченные контексты» в стратегическом документе.
**Типичная ошибка:** карточки без «не владеет»; общие сущности между контекстами («одна таблица User на всех»).

## Шаг 6. Карта контекстов

**Цель.** Описать интеграции: кто кому upstream, что именно течёт, какой тип отношений.

**Как делать.**

1. Стрелки upstream → downstream, подписанные содержимым потока (события, факты, фасады).
2. Тип отношений из книги: partnership (равноправный обмен фактами), customer/supplier, conformist, anticorruption layer (перевод чужой модели на свой язык), open host service + published language.
3. Проверка каждой стрелки: downstream не хранит состояние upstream как источник истины; сбой downstream не откатывает upstream (eventual consistency).

**Тест на слияние двух контекстов — не стрелки, а атомарные инварианты.** Если нет правила, которое должно быть истинным в одной транзакции по обе стороны границы, — границы две, даже если стрелок много.

**Пример рассуждения (кейс: клон Asana).**

> Между двумя BC core-поддомена двусторонняя стрелка. «Может, слить?» Проверяем инварианты: правила Task (один assignee; open/closed независим от размещений) не ссылаются на проекты; правила размещений и полей (один активный placement на пару; значение соответствует типу поля) не ссылаются на lifecycle задачи. Единственная связка — «задача удалена → почистить размещения» — живёт через событие, eventual consistency допустима. Атомарного инварианта через границу нет → границы две; двусторонность — partnership.
>
> Что было бы при слиянии: мешок из семи агрегатов, где изменение типов полей «гремит» рядом с моделью задачи, а слово «статус» означает две вещи в одном пространстве имён.

**Пример переноса.** Интернет-магазин: «Заказы» → «Доставка»: событие `OrderPaid` с адресом и составом — downstream создаёт свою модель доставки. Сбой доставки не откатывает оплату. Если «Доставка» — внешний провайдер (СДЭК API), на границе строится ACL: его модель («PVZ», «tariff code») не просачивается в нашу.

**Артефакт:** карта контекстов (текст + схема).
**Практическая заметка:** mermaid раскладывает диаграмму рангами и растягивает цепочку контекстов в линию; для компактной карты рисуй SVG руками.
**Типичная ошибка:** стрелки без подписи содержимого; синхронные вызовы «вниз» по карте; источник истины, продублированный в двух контекстах.

## Шаг 7. Тактический набросок

**Цель.** Мостик к тактике, не превращаясь в решения.

**Как делать.** Для каждого BC — кандидаты (не решения): Aggregate Roots, Entities, Value Objects, Domain Events, инварианты-кандидаты, политики. Статус «кандидат» снимается только в детальной итерации (шаг 8).

**Пример рассуждения (кейс: клон Asana).**

> «TaskParticipation — кандидат в агрегаты. Гипотеза инварианта: уникальна для пары задача–участник, повторный источник не создаёт дубликат. Статус: кандидат — подтвердим в итерации Work Execution, а не верим на слово».

**Почему «кандидаты», а не сразу решения.** Тактические границы подтверждаются только инвариантами и сценариями. Записанное как решение на стратегическом уровне перестаёт проверяться — и первая же итерация либо ломает документ, либо (хуже) подгоняет модель под документ.

**Артефакт:** раздел «Тактический набросок» в стратегическом документе.
**Типичная ошибка:** расписать тактику до закрытия стратегических вопросов — документ становится нестабильным: стратегия ещё движется, а тактика уже «зафиксирована».

## Шаг 8. Детальные итерации по BC

**Порядок:** от самого upstream вниз по зависимостям — downstream-контексты моделируются с уже известными контрактами upstream.

**Метод каждой итерации.**

1. Граница и язык (таблица терминов, запрещённые слова)
2. Сценарии (команда → событие → политика)
3. Агрегаты и инварианты
4. События двух видов (domain / integration)
5. Открытые вопросы с решениями по умолчанию

### Откуда берутся сценарии — четыре источника

1. **Глаголы возможности** субдомена — они заготовки команд.
2. **Обход жизненного цикла** каждого термина: рождение → изменение → завершение. Все помнят создание, никто — завершение; цикл обязан закрываться.
3. **Обязательства на границах** — что контекст пообещал соседям на карте (шаг 6), то и сценарий.
4. **Боль и эталонный продукт** — боль требует сценария, эталон показывает обязательные.

Симметричное правило отбраковки: сценарий без источника подозрителен; функционал не добирается «для полноты CRUD».

### Как находятся агрегаты — два фильтра

- **Фильтр 1: какой инвариант кандидат защищает?** Агрегат — граница согласованности: правило, истинное после каждой транзакции без окна неопределённости. Нет инварианта — нет агрегата, есть данные. Осторожно с set-based правилами («не более одного X на Y»): они не про содержимое одного объекта и сами по себе агрегат не обосновывают.
- **Фильтр 2: вопросы против вложения.** Есть ли инвариант над всей коллекцией? Меняются ли экземпляры конкурентно? Растёт ли коллекция бесконечно? Ссылаются ли на объект извне по ID (внешние ссылки разрешены только на корни агрегатов)?

### Правило «инварианты рождают функционал»

Записал инвариант → спроси «какая команда может его нарушить и что тогда?» → ответ: запрет или новый сценарий.

### Пример рассуждения 1 (сценарии из источников)

> «Деактивация участника» появилась не из «нужен CRUD», а из двух источников: обход жизненного цикла (membership рождается → меняется → завершается) и боль («уволенный сотрудник не должен видеть задачи»).
>
> «Персональный Workspace» появился из обязательства на границе: мы пообещали downstream «у Task всегда есть Workspace» → кто-то должен создать пространство при регистрации → политика на `AccountRegistered`. В Identity этого сценария нет: Identity не знает слова «workspace» — граница подсказывает, где живёт поведение.

### Пример рассуждения 2 (агрегаты)

> Кандидат WorkspaceMembership. Фильтр 1: «не более одной активной связи на пару Account–Workspace» — set-based, слабо. Фильтр 2: инвариант над коллекцией? Нет. Конкурентность? Два админа меняют разных участников одновременно — да. Рост? Коллекция растёт с размером компании — да. Внешние ссылки по `WorkspaceMemberId` из рабочих контекстов — да, и это решающе. Вердикт: отдельный корень, не коллекция внутри Workspace.

### Пример рассуждения 3 (инварианты рождают функционал)

> Инвариант «ровно один owner на Workspace». Какой агрегат гарантирует его атомарно? Membership не видит множества; проверка через репозиторий — гонка (два одновременных запроса оба «проверили»). Факт владения поднимается туда, где он единственный: `Workspace.ownerMembershipId`.
>
> Какая команда может нарушить? «Owner выходит из пространства». Запретить? А если он увольняется? Инвариант породил новый обязательный сценарий: `TransferOwnership` — его не было ни в одном источнике, его породил сам инвариант.

### Пример рассуждения 4 (симметрия с памятью о причине)

> Есть блокировка аккаунта → делаем симметричную разблокировку. Наивная реакция на `AccountUnblocked`: реактивировать все memberships. Баг: админ вручную деактивировал уволенного → аккаунт блокируют/разблокируют по другой причине → уволенный вернулся. Решение: membership запоминает причину деактивации (`manual | accountBlocked`), политика реактивирует только «своих». Правило: симметричные событийные реакции — только с памятью о причине.

**Артефакт:** файл итерации на каждый BC + журнал «что итерация изменила в стратегической карте».
**Типичная ошибка:** агрегаты, скопированные с существительных; инварианты, «проверяемые» в application-слое через запрос (гонка); события с жирным payload, превращающие downstream в скрытую копию upstream.

## Сквозные практики

- **Единый язык** — глоссарий с колонкой «важное различие»; обновляется каждой итерацией.
- **Hotspots** — открытые вопросы фиксируются со статусом и решением по умолчанию, становятся повесткой, а не фоновой тревогой.
- **Триггеры пересмотра** — для каждого «не выделяем» записано условие, при котором решение пересматривается.
- **Эталонный продукт** — сверка по каждому спорному вопросу; отклонения документируются.
- **Сохранение рассуждений** — в docs пишется ход мысли, не только выводы: через полгода ценность именно в «почему».

## Чеклист здоровья разбиения

- Каждый BC отвечает на свой вопрос одной фразой и не отвечает на чужие.
- Нет контекста-мешка с 5+ агрегатами разных причин изменений.
- Классификация обоснована дифференциатором, не тавтологией.
- Нет атомарных инвариантов через границу BC (есть → граница не там).
- Каждая связь на карте подписана содержимым и направлением.
- У каждого «не субдомена» записано, где он живёт, и триггер выделения.
- Все hotspots имеют статус и владельца решения.

## Типичные ошибки (свод)

1. Нарезка по существительным вместо деятельности → god-контекст.
2. Тавтологическая классификация core («core, потому что важно»).
3. Смешение стратегии и тактики в одном документе до закрытия стратегии.
4. Выделение механики (доступ) в субдомен без тестов отдельности.
5. Инвариант, «проверяемый через репозиторий» в app-слое, — гонка; поднимай факт туда, где он атомарен.
6. Симметричные событийные реакции без памяти о причине.
7. Mermaid для карт с двусторонними связями — растянет в линию; рисуй SVG.
8. Классификация по технической сложности вместо бизнес-дифференциации.
