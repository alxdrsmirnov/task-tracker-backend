# Discovery 03: Субдомены из возможностей и модель доступа

> Шаги стратегического анализа: слипание возможностей в кандидатов на субдомены; разбор, почему доступ — не субдомен; модель доступа Asana и её раскладка по субдоменам.

## Слипание возможностей

Метод: группировка возможностей (см. 02) по трём признакам — общий язык, общая причина изменений, общая бизнес-цель. Правило скепсиса: новая группа появляется только с доказанной причиной; по умолчанию возможности живут вместе.

Результат:

| Кандидат | Возможности | Ключевой аргумент |
| --- | --- | --- |
| Исполнение работы | 1, 2, 5, 6 | Язык работы и её исполнения; обсуждение внутри до триггера |
| Организация работы | 3, 4 | Свой язык представлений и настройки; своя причина изменений |
| Структура компании | 9 | Орг-язык и орг-причины изменений |
| Уведомления | 8 | Реагирует, не управляет; свой язык получателя и истории |
| Установление личности | 10 | Commodity-деятельность без слов домена |
| Определение доступа | 7 | **Не субдомен** — политики внутри владеющих групп |

Ключевые решения при слипании:

- Разрез «Исполнение vs Организация» — самый важный: в UI и коде группы сольются (проект показывает задачи), но деятельность разная — «вести работу» и «организовывать представления работы» говорят разными языками и меняются по разным причинам.
- Обсуждения (6) внутри Исполнения: у комментариев нет инвариантов, не связанных с задачей. Триггер выделения Collaboration: модерация, треды, реакции, история редактирования или второй носитель комментариев.
- Уведомления (8) — отдельно: реагируют, а не управляют; сбой не должен ломать работу.
- «Поручить» включает «уведомить» — это не отдельная возможность, а связь между группами: набросок карты контекстов.

## Почему «Определение доступа» — не субдомен

### Что показывает пример Вернона на самом деле

В красной книге у SaaSOvation есть отдельный Identity and Access Context, но туда попали `Tenant`, `User`, аутентификация, подписки — идентичность плюс доступ грубого уровня («какой пользователь, в каком тенанте»). Права на доменные объекты НЕ вынесены: решения «может ли человек редактировать backlog item» принимает сам AgilePM (core). Доменные роли (`ProductOwner`, `TeamMember`) — объекты AgilePM-модели, получаемые адаптером из сырых фактов IAM.

Причины отдельности IAM у SaaSOvation: переиспользуемый и отдельно продаваемый продукт люкса; собственный язык без слов потребителей; собственное состояние и lifecycle.

### Тесты на отдельность для нашей возможности 7

- Свой язык? Нет: правила звучат чужими словами («editor проекта», «участник задачи», «видимость»). Отдельный контекст доступа был бы зеркалом обоих core — паразитная связанность.
- Своя бизнес-цель? Нет: enabling-механика.
- Своё состояние и lifecycle? Нет: роли фиксированные enum'ы, политики stateless.

Вердикт: доступ — stateless-политики внутри контекстов-владельцев. Триггер выделения в субдомен: настраиваемое состояние с lifecycle — кастомные роли, редактор политик, временный доступ, share-ссылки, аудит.

Аналогично книге отличается и Collaboration: у Вернона отдельный контекст имел собственные сложные модели (Forum, Discussion, Calendar); у нас — только комментарии к задачам. Принцип: книга — не каталог готовых границ, а набор тестов на отдельность.

## Модель доступа Asana

Четыре уровня-слоя, каждый владеет своей частью:

1. **Организация/Workspace**: роли super admin / admin / member / guest. Guest видит только явно расшаренное.
2. **Team**: контейнер доступа к проектам; у проекта организации ровно одна команда-владелец; членство в команде даёт доступ к её публичным проектам; приватность команды: открытая / по запросу / скрытая.
3. **Project**: фиксированные роли admin / editor / commenter / viewer; приватность: приватный или публичный на workspace; настройки уровня доступа по умолчанию.
4. **Task**: collaborator — слитое понятие (прямой доступ + подписка на обновления); автопопадание: создатель, assignee, комментатор, упомянутый. Доступ к задаче = объединение источников, берётся максимум (viewer в одном проекте + editor в другом = editor на задаче). Приватная задача без проектов — только collaborators. Assigned-task elevation: assignee получает повышенные права независимо от проектной роли. Request access — сценарий запроса доступа с маршрутизацией.

## Раскладка модели доступа по нашим субдоменам

| Часть модели Asana | Где живёт у нас | В каком виде |
| --- | --- | --- |
| Workspace-роли (owner/admin/member; guest отложен) | Workspace | Enum `WorkspaceRole` внутри `WorkspaceMembership` |
| Состав людей и его активность | Workspace | Агрегаты membership + события для остальных контекстов |
| Проектные роли и членство | Work Organization | Enum `ProjectRole`, агрегат `ProjectMembership` |
| «Что роль может в проекте» | Work Organization | `ProjectAccessPolicy` — stateless-таблица capability × role |
| Приватность задачи, collaborators | Work Execution | `TaskVisibility` на Task, агрегат `TaskParticipation` (sources + subscribed) |
| «Что ты можешь с этой задачей» | Work Execution | `TaskAccessPolicy` — MAX-merge, скрытие недоступных проектов, 404 |
| Уведомления | Notification | Доступом не занимается; получателей даёт участие |

Взаимодействие: Workspace публикует факты членства → рабочие контексты потребляют; Work Organization поставляет Work Execution факты размещений и проектного членства; политики вычисляются внутри владеющего контекста при обработке команды/запроса. Нет центрального «сервиса доступа»: каждый владелец решает сам, фактами соседей пользуется.

Сознательные отклонения от Asana: team membership не даёт проектных прав автоматически; гости, assigned-task elevation и request access отложены (см. `docs/domain-model.md`, «Отложенные вопросы»).
