# Бизнес-сценарии

> Результат шага 3 стратегического анализа DDD.
>
> Статус панорамы: подтверждено пользователем 23.08.2026.

## Назначение документа

Документ фиксирует широкую панораму поведения целевого Asana-подобного продукта. Он показывает значимые цели участников и наблюдаемые результаты по всей подтверждённой границе, а не только центральный сценарий работы с Task.

Сценарии пока не являются субдоменами, ограниченными контекстами, API-операциями или требованиями к структуре кода.

Поведение Asana проверено по официальной документации 23.08.2026 и используется как эталон. Для целевого продукта оно считается принятым только в той мере, в которой отражено в подтверждённых формулировках ниже.

## Охваченные области

1. Учётная запись и вход.
2. Workspace, Teams, Members и Guests.
3. Доступ и приватность.
4. Projects.
5. Tasks.
6. My Tasks.
7. Мультипроектность и Custom Fields.
8. Обсуждение работы.
9. Inbox и уведомления.
10. Forms, Templates и Rules.
11. Поиск и отчётность.
12. Администрирование и прекращение доступа.
13. Поздние возможности: Goals, Portfolios, Workload, интеграции и enterprise-функции.

## Каталог сценариев

### 1. Учётная запись и вход

| Сценарий                                                | Наблюдаемый результат и важное правило                                                 |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Человек регистрируется                                  | Создаётся личная Account. Она не принадлежит исключительно одному Workspace.           |
| Пользователь входит, выходит или восстанавливает пароль | Он получает или восстанавливает доступ, не изменяя членство в Workspace.               |
| Пользователь усиливает безопасность                     | Он включает 2FA; обязательный SSO относится к позднему enterprise-горизонту.           |
| Пользователь состоит в нескольких Workspace             | Одна Account позволяет переключаться между изолированными пространствами.              |
| Пользователь деактивирует Account                       | Он теряет личный доступ, но общие Workspace и созданная им история работы не исчезают. |

### 2. Workspace, участники и Teams

| Сценарий                                   | Наблюдаемый результат и важное правило                                                                   |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| Пользователь создаёт Workspace             | Появляется самостоятельная граница людей и принадлежащей ей работы.                                      |
| Участник приглашает сотрудника             | После принятия приглашения человек становится Member. Отмена приглашения делает ссылку недействительной. |
| Участник приглашает клиента или подрядчика | Человек становится Guest и видит только явно открытую ему работу.                                        |
| Участник создаёт Team                      | Появляется устойчивая группа людей внутри Workspace.                                                     |
| Member вступает в Team                     | Для публичной Team это происходит напрямую, для закрытой — по приглашению или после одобрения запроса.   |
| Администратор меняет роли                  | Workspace Admin, Team Admin и обычное членство дают полномочия разного масштаба.                         |
| Человек покидает Team                      | Он теряет доступ, полученный через Team, но может сохранить прямой доступ к Projects или Tasks.          |
| Человек покидает Workspace                 | Прекращается конкретное Workspace Membership, а не существование Account.                                |

Целевой продукт использует единый термин `Workspace`, не повторяя различие Asana между Organization и Workspace.

### 3. Доступ и приватность

| Сценарий                                       | Наблюдаемый результат и важное правило                                                     |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Project открывают всему Workspace              | Все Members получают доступ, но Guests автоматически его не получают.                      |
| Project открывают Team                         | Доступ появляется у участников этой Team.                                                  |
| Человека добавляют непосредственно в Project   | Он получает доступ независимо от Team Membership и свою проектную роль.                    |
| Человека добавляют Collaborator отдельной Task | Он видит эту Task, но не обязательно весь Project.                                         |
| Task находится в нескольких Projects           | Пути доступа суммируются; предлагается применять наибольший полученный уровень разрешений. |
| Пользователь запрашивает доступ                | Уполномоченный участник принимает или отклоняет запрос.                                    |
| Доступ требуется отозвать                      | Необходимо устранить все его источники: Workspace, Team, Project и прямой доступ к Task.   |

### 4. Projects

| Сценарий                                        | Наблюдаемый результат и важное правило                                                                   |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Команда создаёт Project                         | Появляется пространство для организации инициативы или постоянного процесса.                             |
| Владелец настраивает Project                    | Определяются назначение, владелец, сроки, участники, роли и приватность.                                 |
| Редактор создаёт Sections                       | Tasks группируются по этапам, периодам, категориям или другому локальному смыслу.                        |
| Участник перемещает Task между Sections         | Меняется её положение внутри конкретного Project, а не глобальное состояние Task.                        |
| Участник выбирает представление                 | List, Board, Calendar или Timeline показывают одну работу разными способами.                             |
| Команда сохраняет Project как Template          | Новые Projects получают заранее подготовленную структуру процесса.                                       |
| Руководитель публикует Project Status           | Фиксируется снимок здоровья Project, например `On track` или `At risk`. Это не состояние отдельной Task. |
| Project завершают, переоткрывают или архивируют | Его жизненный цикл изменяется независимо от завершения входящих в него Tasks.                            |

### 5. Tasks

| Сценарий                                     | Наблюдаемый результат и важное правило                                                                                 |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Участник фиксирует работу                    | Task создаётся внутри Project либо отдельно от Projects.                                                               |
| Автор описывает ожидаемый результат          | У Task появляются название, описание, вложения и другой общий контекст.                                                |
| Координатор назначает ответственного         | У Task один Assignee; Task появляется в его My Tasks.                                                                  |
| К работе подключают других людей             | Несколько Collaborators участвуют в обсуждении и следят за изменениями, но не делят ответственность Assignee.          |
| Участник задаёт сроки                        | Start Date и Due Date являются общими свойствами Task.                                                                 |
| Крупную работу разбивают                     | Subtasks имеют собственных ответственных, сроки и состояние.                                                           |
| Между Tasks задают зависимость               | Завершение блокирующей работы уведомляет следующего исполнителя, но не обязательно технически запрещает начать раньше. |
| Создают повторяющуюся работу                 | После завершения появляется следующий экземпляр Task, а не переоткрывается старая.                                     |
| Работу обозначают как Milestone или Approval | Task получает специализированный бизнес-смысл; необходимость этих типов для клона требует отдельного решения.          |
| Исполнитель завершает Task                   | Общая Task становится завершённой во всех Projects.                                                                    |
| Участник переоткрывает Task                  | Возобновляется та же Task с сохранённой историей.                                                                      |
| Task удаляют из одного Project               | Исчезает только её размещение; сама Task и остальные размещения сохраняются.                                           |

### 6. My Tasks

| Сценарий                             | Наблюдаемый результат и важное правило                                                  |
| ------------------------------------ | --------------------------------------------------------------------------------------- |
| Человеку назначают Task              | Она автоматически появляется в его My Tasks независимо от исходного Project.            |
| Человек создаёт личную Task          | Появляется приватная Task без обязательного Project.                                    |
| Человек организует свою работу       | Создаёт личные Sections, фильтры и Views, не изменяя организацию командных Projects.    |
| Человек задаёт персональные признаки | Использует личные Custom Fields, которые не обязательно видят остальные участники Task. |
| Человек автоматизирует планирование  | Персональные Rules распределяют работу, например по срокам или личным Sections.         |

My Tasks рассматривается как персональная проекция общих Tasks и отдельный способ личной организации, а не как второй владелец рабочих данных Task.

### 7. Мультипроектность и Custom Fields

| Сценарий                                   | Наблюдаемый результат и важное правило                                                                 |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| Одна работа нужна нескольким командам      | Одна Task добавляется в несколько Projects без копирования.                                            |
| Общий факт Task изменяется                 | Название, описание, Assignee, сроки, комментарии и завершённость обновляются для всех Projects.        |
| Task перемещается внутри одного Project    | Section и позиция изменяются только в этом Project.                                                    |
| Project добавляет собственный Custom Field | Команда получает локальный способ классифицировать работу.                                             |
| Workspace публикует общий Custom Field     | Одно определение поля переиспользуется несколькими Projects.                                           |
| Участник задаёт Custom Field Value         | Значение становится частью описания работы; точная область его принадлежности требует решения.         |
| Создаётся Custom Task Type со Statuses     | В современной Asana тип и статус следуют за Task между Projects и могут влиять на Complete/Incomplete. |

Обычный Custom Field с названием `Status` и Custom Task Status — разные механизмы. Нельзя автоматически считать современный Custom Task Status проектно-локальным состоянием размещения Task.

### 8. Обсуждение работы

| Сценарий                                   | Наблюдаемый результат и важное правило                                                      |
| ------------------------------------------ | ------------------------------------------------------------------------------------------- |
| Участник комментирует Task                 | Комментарий сохраняется в истории работы; Collaborators получают уведомление.               |
| Пользователь упоминает человека            | Тот получает адресное уведомление и в эталонной Asana становится Collaborator Task.         |
| Человека вручную добавляют Collaborator    | Он получает прямой доступ и подписывается на обновления Task.                               |
| Collaborator покидает Task                 | Уведомления прекращаются, но доступ через Project может сохраниться.                        |
| Участник прикладывает файл                 | Вложение становится частью контекста Task.                                                  |
| Участник прикладывает внешний файл         | Task хранит ссылку, но права внешнего хранилища остаются независимыми.                      |
| Участник упоминает другую Task или Project | Между рабочими объектами появляется ссылка, доступная только имеющим соответствующие права. |

### 9. Inbox и уведомления

| Сценарий                                                           | Наблюдаемый результат и важное правило                                                      |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| Пользователю назначают Task                                        | Он получает персональное уведомление.                                                       |
| В наблюдаемой Task появляется комментарий, вложение или завершение | Collaborators получают обновление.                                                          |
| Пользователя упоминают                                             | Создаётся адресное уведомление.                                                             |
| В наблюдаемом Project появляется важное изменение                  | Project Members получают уведомления согласно персональным и проектным настройкам.          |
| Пользователь выполняет действие сам                                | Собственное действие не создаёт уведомление в его Inbox.                                    |
| Пользователь читает, архивирует или сохраняет уведомление          | Изменяется только его персональное состояние Inbox, а не исходная Task.                     |
| Пользователь выбирает каналы доставки                              | Inbox, email, browser или внешние каналы получают одно событие по разным правилам доставки. |

Формирование персонального потока внимания уже выглядит самостоятельной бизнес-возможностью, но отдельный `Notification BC` на этом шаге ещё не объявляется.

### 10. Forms, Templates и Rules

| Сценарий                                       | Наблюдаемый результат и важное правило                                                   |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Владелец процесса публикует Form               | Появляется структурированный канал приёма запросов в конкретный Project.                 |
| Внутренний или внешний человек отправляет Form | Submission превращается в новую Task.                                                    |
| Ответы формы сопоставляются полям              | Данные переводятся в название, описание, вложения и Custom Fields Task.                  |
| Запрос маршрутизируется                        | Task получает начальную Section или Assignee.                                            |
| Команда создаёт Project из Template            | Возникает новый экземпляр типового процесса.                                             |
| Владелец создаёт Rule                          | Настраивается реакция `trigger → conditions → actions`.                                  |
| В Task происходит настроенное событие          | Rule назначает человека, меняет поле, перемещает Task или выполняет другое действие.     |
| Конфигурация Rule изменяется                   | Новые правила действуют только на будущие срабатывания.                                  |
| Rule ссылается на удалённую Section или Field  | Она становится неисправной, а владелец получает предупреждение вместо фиктивного успеха. |

Rules настраивают локальный процесс, но не превращают его в универсальный жизненный цикл Task.

### 11. Поиск и отчётность

| Сценарий                                 | Наблюдаемый результат и важное правило                                      |
| ---------------------------------------- | --------------------------------------------------------------------------- |
| Пользователь ищет известную работу       | Находит Tasks, Projects, Teams и людей по доступному содержимому.           |
| Координатор формирует рабочую выборку    | Фильтрует Tasks по Assignee, Project, датам, завершённости и Custom Fields. |
| Пользователь сохраняет поиск             | Сохраняются критерии, а результаты обновляются вместе с системой.           |
| Два человека выполняют одинаковый поиск  | Результаты различаются в зависимости от доступных им объектов.              |
| Руководитель оценивает состояние Project | Получает сводку по срокам, завершённости, рискам и Project Status.          |

Поиск и отчётность никогда не должны расширять доступ пользователя к исходной работе.

### 12. Администрирование и прекращение доступа

| Сценарий                                      | Наблюдаемый результат и важное правило                                                  |
| --------------------------------------------- | --------------------------------------------------------------------------------------- |
| Admin управляет составом Workspace            | Видит Members, Guests, приглашения и роли.                                              |
| Admin ограничивает приглашения или приложения | Общая политика Workspace ограничивает локальные действия участников.                    |
| Admin исключает сотрудника                    | Доступ прекращается, но Tasks, Projects, comments и files сохраняются.                  |
| Работа ушедшего сотрудника перераспределяется | Его незавершённые Tasks передаются другому ответственному либо остаются неназначенными. |
| Admin восстанавливает Membership              | Человек возвращается; требуется решить, восстанавливаются ли прежние доступы.           |
| Человек удаляет личную Account                | Это не то же самое, что исключение из Team или Workspace.                               |

## Поздний горизонт

Эти сценарии видны в панораме зрелого продукта, но пока не углубляются:

| Область                | Бизнес-сценарий                                                                         |
| ---------------------- | --------------------------------------------------------------------------------------- |
| Goals                  | Руководители связывают ежедневную работу со стратегическими целями и измеряют прогресс. |
| Portfolios             | Руководители объединяют Projects и наблюдают их здоровье и риски.                       |
| Workload               | Координаторы оценивают загрузку людей и перераспределяют работу.                        |
| Расширенная отчётность | Пользователи строят общие dashboards по Tasks, Projects, Custom Fields и Goals.         |
| Интеграции             | Участники связывают работу с внешними системами и действиями Rules.                     |
| Enterprise Security    | Администраторы используют SSO, SCIM, Custom RBAC, Audit и общие security-политики.      |
| Billing                | Владелец подписки управляет тарифом и коммерческим доступом к возможностям.             |

## Общие правила и варианты поведения

1. `Account`, `Workspace Membership` и доступ к конкретной работе имеют разные жизненные циклы.
2. Одна `Task` может существовать без Project и одновременно находиться в нескольких Projects.
3. У Task один ответственный, но несколько участников обсуждения.
4. Общие факты Task не копируются между Projects.
5. Project задаёт локальную организацию процесса, но не владеет всей Task.
6. My Tasks добавляет персональную организацию поверх общих Tasks.
7. Доступ может складываться из нескольких независимых источников.
8. Участие в Task связано с доступом и уведомлениями, но эти понятия не тождественны.
9. Notification является персональным результатом произошедшего события, а не частью исходной Task.
10. Rules настраивают процесс, но не определяют универсальный жизненный цикл работы.
11. Поиск и отчётность не расширяют полномочия пользователя.
12. Прекращение членства не стирает историю организации.

## Hotspots для углубления

### 1. Общая Task и локальный Project

Необходимо определить, какие данные принадлежат общей Task, а какие — её размещению в конкретном Project.

### 2. Custom Field, Status и Complete

Нужно разделить:

- произвольное поле с названием `Status`;
- Custom Task Status;
- локальный workflow Project;
- глобальное Complete/Incomplete одной Task.

### 3. Доступ к multi-homed Task

Нужно определить правила объединения Workspace, Team, Project, Guest и прямого Task-доступа, а также порядок полного отзыва доступа.

### 4. Task Collaborator

Необходимо понять, являются ли прямой доступ, участие в обсуждении и подписка на обновления одной моделью или связанными, но раздельными решениями.

### 5. My Tasks

Нужно провести границу между общей Task и приватными Sections, Fields, Views и Rules конкретного пользователя.

### 6. Прекращение Membership

Нужно определить судьбу ответственности, прямых доступов, подписок и персональных настроек ушедшего сотрудника, а также правила восстановления.

### 7. Внешний заявитель Form

Нужно решить, как внешний человек получает результат и продолжает обсуждение после превращения Submission в Task.

## Предположения и пробелы

- Аддитивный доступ и выбор наибольшего разрешения пока приняты как предлагаемая базовая модель по образцу Asana; детали будут проверены при углублении hotspot доступа.
- Один Assignee, общая Completion и возможность личных Tasks приняты в текущую модель.
- Точная принадлежность Custom Field Value пока не определена.
- Milestones и Approvals присутствуют в панораме, но их необходимость для целевого продукта не подтверждена отдельно.
- Формирование Notifications выглядит самостоятельной бизнес-возможностью, но граница ограниченного контекста относится к шагам 4–6.
- Поздние возможности не должны определять раннюю тактическую модель, но могут повлиять на будущий пересмотр стратегических границ.
