# Доменные события и бизнес-правила

> Результат шага 3 стратегического анализа DDD.
>
> Статус: подтверждено пользователем 04.09.2026, актуализировано 05.09.2026.

## Назначение документа

Документ преобразует подтверждённые бизнес-сценарии в панораму значимых бизнес-фактов и правил целевого Asana-подобного продукта. Стрелки показывают причинную последовательность событий, а не зависимости будущих ограниченных контекстов.

Это ещё не декомпозиция на субдомены или ограниченные контексты и не проектирование агрегатов, таблиц, API или программного кода.

Основанием служат [описание домена](domain-model.md) и [каталог бизнес-сценариев](business-scenarios.md).

## 1. Account и личный доступ

### События

```text
Account создана
Личность пользователя подтверждена → Доступ к Account получен
Восстановление доступа запрошено → Личность подтверждена → Доступ восстановлен
2FA включена
Account деактивирована → Личный доступ прекращён
```

### Правила

- Одна Account может участвовать в нескольких Workspace.
- Вход, выход и восстановление пароля не изменяют членство в Workspace.
- Деактивация Account не удаляет Workspace, Tasks, комментарии и историю работы.
- Account, членство в Workspace и членство в Team — разные понятия.

## 2. Workspace, участники и Teams

### События

```text
Workspace создан
```

```text
Приглашение сотруднику создано
→ Приглашение принято
→ Человек стал Member Workspace
```

```text
Приглашение внешнему участнику создано
→ Приглашение принято
→ Человек стал Guest Workspace
```

```text
Team создана
→ Member вступил в Team
```

Для закрытой Team:

```text
Запрос на вступление отправлен
→ Запрос одобрен
→ Member вступил в Team
```

Также:

```text
Роль участника изменена → Полномочия участника изменились
Членство в Team прекращено
Членство в Workspace прекращено
```

### Правила

- Team существует только внутри Workspace.
- Team Membership не заменяет Workspace Membership.
- Guest видит только явно предоставленную ему работу.
- Выход из Team отзывает только доступы, полученные через эту Team.
- Выход из Workspace не удаляет Account человека.

## 3. Доступ и приватность

### События

```text
Project открыт всему Workspace
→ Members получили доступ к Project
```

```text
Project открыт Team
→ Участники Team получили доступ к Project
```

```text
Человек добавлен в Project
→ Прямой доступ предоставлен
→ Проектная роль назначена
```

```text
Человек добавлен Collaborator Task
→ Прямой доступ к Task предоставлен
→ Наблюдение за Task началось
```

```text
Доступ запрошен
→ Запрос одобрен / отклонён
→ Доступ предоставлен / не предоставлен
```

```text
Источник доступа устранён
→ Остальные источники проверены
→ Доступ сохранён или полностью отозван
```

### Правила

- У одной Task может быть несколько независимых источников доступа.
- Удаление одного источника не отзывает доступ, если остаётся другой.
- Доступ к Task через Project не даёт доступ ко всем остальным Projects этой Task.
- Доступ ко всему Workspace автоматически не распространяется на Guests.
- Полный отзыв требует устранить все источники доступа.

## 4. Projects

### События

```text
Project создан
→ Назначение Project определено
→ Владелец, сроки, участники и приватность настроены
```

```text
Section создана
→ Task размещена в Section
→ Task перемещена в другую Section
```

```text
Представление Project настроено
```

```text
Project Status опубликован
→ Снимок здоровья Project зафиксирован
```

```text
Project завершён
Project переоткрыт
Project архивирован
```

### Правила

- Project может описывать временную инициативу или постоянный процесс.
- Section и положение Task имеют смысл только внутри конкретного Project.
- Перемещение Task в Project не изменяет её положение в остальных Projects.
- List, Board, Calendar и Timeline показывают одну и ту же работу.
- Project Status — оценка здоровья Project, а не состояние отдельной Task.
- Завершение или архивирование Project не завершает его Tasks автоматически.

## 5. Tasks

### События

```text
Task создана
→ Ожидаемый результат описан
→ Ответственный назначен
→ Сроки установлены
→ Task завершена
```

```text
Task завершена → Task переоткрыта
```

```text
Subtask создана
Зависимость между Tasks установлена
```

```text
Повторение Task настроено
→ Task завершена
→ Следующий экземпляр Task создан
```

### Правила

- Task может быть создана внутри Project или независимо от Projects.
- У Task один Assignee и несколько Collaborators.
- Название, описание, Assignee, сроки и завершённость принадлежат общей Task.
- Subtask имеет собственную ответственность, сроки и завершённость.
- Переоткрывается та же Task с сохранённой историей.
- Зависимость показывает порядок работы, но пока не считается строгим запретом на начало другой Task.
- Milestone и Approval пока остаются неподтверждёнными возможностями зрелого продукта.

## 6. My Tasks

### События

```text
Ответственный назначен
→ Task появилась в My Tasks ответственного
```

```text
Личная Task создана
→ Task появилась в My Tasks создателя
```

```text
Личная Section создана
→ Task размещена в личной Section
→ Task перемещена в другую личную Section
```

```text
Персональное Rule настроено
→ Условие выполнено
→ Персональная организация Task изменена
```

### Правила

- My Tasks не создаёт копий Tasks.
- Назначенная человеку Task автоматически появляется в его My Tasks.
- Личные Sections, порядок и представления не изменяют командные Projects.
- Приватная личная Task может существовать без Project.
- Персональная организация одного человека не должна менять представление другого.

## 7. Мультипроектность и Custom Fields

### События

```text
Task добавлена в Project
→ Размещение Task создано
→ Task размещена в Section
```

```text
Task добавлена в другой Project
→ Дополнительное размещение создано
```

```text
Общие сведения Task изменены
→ Изменения стали видны во всех её Projects
```

```text
Task удалена из одного Project
→ Одно размещение прекратилось
→ Task сохранилась в остальных Projects
```

```text
Custom Field создано
→ Custom Field подключено к Project
→ Custom Field Value установлено
```

```text
Custom Field опубликовано в Workspace
→ Определение подключено к нескольким Projects
```

```text
Custom Task Type создан
→ Допустимые проектные Statuses определены
→ Status Task установлен
```

### Правила

- Мультипроектность не создаёт копий Task.
- Общие свойства Task одинаковы во всех Projects.
- Section и позиция относятся к конкретному размещению.
- Глобальная завершённость Task и её проектный Status — разные состояния.
- Завершение Task не меняет `TODO / DOING / CHECK / DONE` автоматически.
- Такое изменение может выполнить отдельно настроенное Rule.

## 8. Обсуждение работы

### События

```text
Комментарий опубликован
→ Участники Task получили обновление
```

```text
Пользователь упомянут
→ Адресное уведомление создано
→ Пользователь подключён к Task
```

```text
Collaborator добавлен
→ Прямой доступ предоставлен
→ Подписка на обновления началась
```

```text
Collaborator покинул Task
→ Подписка на обновления прекращена
```

```text
Файл прикреплён к Task
Ссылка на другую Task или Project создана
```

### Правила

- Комментарии и вложения являются частью контекста работы.
- Выход из Collaborators прекращает уведомления, но доступ через Project может сохраниться.
- Ссылка на другую Task или Project не предоставляет доступ к ним.
- Автоматическое подключение упомянутого человека — подтверждённое поведение Asana, но ещё не отдельное продуктовое решение целевого продукта.

## 9. Notification и Inbox

### События

```text
Task назначена / добавлена в Project
→ Получатели определены
→ Персональные Notifications созданы
```

```text
Комментарий опубликован
Task завершена или переоткрыта
Пользователь упомянут
→ Notifications созданы для соответствующих участников
```

```text
Notification создано
→ Доставлено в Inbox и выбранные каналы
→ Прочитано / архивировано / сохранено
```

```text
Настройки доставки изменены
→ Последующие Notifications доставляются по новым правилам
```

### Правила

- У каждого получателя собственное состояние Notification.
- Чтение или архивирование Notification не изменяет исходную Task.
- Автор действия не получает Notification о собственном действии.
- Упоминание и назначение Assignee создают адресные Notifications.
- Inbox, email и browser — разные способы доставки одного бизнесового изменения.

## 10. Forms, Templates и Rules

### Forms

```text
Form опубликована
→ Submission отправлена
→ Submission принята
→ Task создана
→ Ответы перенесены в свойства Task
→ Task размещена и назначена
```

Правила:

- Внешний заявитель может отправить Form, не вступая в Workspace.
- Настройка Form определяет преобразование ответов и начальную маршрутизацию Task.

### Templates

```text
Project сохранён как Template
→ Создание Project запрошено
→ Новый Project создан
→ Шаблонная структура применена
```

Новый Project является отдельным экземпляром процесса, а не продолжением Template.

### Rules

```text
Rule настроено
→ Значимое событие произошло
→ Условия Rule выполнены
→ Настроенные действия произошли
```

Пример:

```text
Task завершена
→ Условия Rule выполнены
→ Проектный Status установлен в DONE
→ Task перемещена в Section «Готово»
```

Правила:

- Rule описывает `событие → условия → действия`.
- Действия Rule создают обычные бизнесовые события.
- Удалённое Field или Section не должно приводить к незаметно неправильному действию: Rule становится неисправным.

## 11. Поиск и отчётность

Обычный поиск не обязательно порождает доменное событие: пользователь лишь получает ответ.

Изменяющие состояние события:

```text
Поиск сохранён
Критерии сохранённого поиска изменены
Dashboard сохранён
Project Status опубликован
```

### Правила

- Сохранённый поиск хранит критерии, а не снимок результатов.
- Два пользователя с одинаковыми критериями могут получить разные результаты из-за доступа.
- Отчётность не должна раскрывать недоступную работу.
- Project Status является опубликованной оценкой, а вычисляемые показатели строятся по текущему состоянию работы.

## 12. Администрирование и offboarding

### События

```text
Политика Workspace изменена
→ Допустимые действия участников изменились
```

```text
Членство сотрудника в Workspace прекращено
→ Источники доступа через Workspace и Teams прекратились
→ Незавершённая работа сотрудника обнаружена
→ Tasks переназначены или остались без Assignee
```

```text
Членство в Workspace восстановлено
→ Разрешённый доступ возобновлён
```

### Правила

- Исключение из Workspace не удаляет Account.
- Tasks, Projects, комментарии, файлы и авторство сохраняются.
- Исключение из Team, Workspace и деактивация Account — разные операции.
- Восстановление старых Team Membership и прямых доступов пока не определено.

## Показательные сквозные цепочки

### Одна Task в нескольких процессах

```text
Task создана
→ Добавлена в Project продаж
→ Добавлена в Project разработки
→ Проектный Status разработки изменён на DOING
→ Task глобально завершена
→ Завершённость стала видна в обоих Projects
→ Проектные Statuses сохранились
→ Rule разработки изменило Status на DONE
```

### Внешний запрос превращается в работу

```text
Form отправлена
→ Task создана
→ Task добавлена в Project
→ Custom Fields заполнены
→ Assignee назначен
→ Notification создано
```

### Сотрудник покидает компанию

```text
Workspace Membership прекращено
→ Командные источники доступа прекратились
→ Оставшиеся источники доступа проверены
→ Незавершённые Tasks найдены
→ Ответственность перераспределена
```

## Стратегические открытые вопросы

Эти вопросы могут повлиять на последующее выделение субдоменов и ограниченных контекстов:

1. Как окончательно разделяются `Collaborator`, прямой доступ к Task и подписка на её обновления?
2. Где находится `Custom Field Value`: у общей Task или у её размещения в конкретном Project?
3. Что именно восстанавливается при повторном вступлении человека в Workspace?
4. Какие персональные Custom Fields в My Tasks видны другим участникам общей Task?
5. Включаются ли Milestones и Approvals в целевую модель или откладываются?

Редактирование комментариев, точный порядок нескольких Rules, история поиска и подобные детали не исследуются на этом шаге, пока они не влияют на стратегическую декомпозицию.
