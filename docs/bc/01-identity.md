# BC 01: Identity

> Детальная итерация по контексту Identity (Generic).
> Метод итерации: граница и язык → сценарии (команда → событие → политика) → агрегаты и инварианты → события (domain/integration) → открытые вопросы.

## Назначение и граница

Identity отвечает ровно на два вопроса: «этот человек существует?» и «этот человек — тот, за кого себя выдаёт?». Всё, что отвечает на вопрос «что ему можно» — вне этого контекста (Workspace и далее).

Владеет: Account, credentials, password authentication, sessions и refresh tokens, состояние аккаунта.

Не владеет: Workspace, membership, Team, Project, Task, любыми бизнес-ролями. Запрещённые слова языка: workspace, member, task, project, role.

## Единый язык

| Термин | Значение | Различие |
| --- | --- | --- |
| `Account` | Глобальная учётная запись человека | Не WorkspaceMember; ничего не знает о пространствах |
| `Email` | Канонический адрес аккаунта | Нормализуется (lower-case, trim) до сравнения |
| `Credentials` | Способ доказать личность | Сейчас — только пароль; второй способ = отдельное решение |
| `PasswordHash` | Хэш пароля | Пароль в открытом виде нигде не живёт |
| `AccountStatus` | `active` \| `blocked` | Подтверждение email отложено, статус `pending` не вводим |
| `Session` | Активный сеанс доступа | Отдельный агрегат, не коллекция в Account |
| `RefreshTokenHash` | Хэш токена продления сессии | Сырой токен не хранится |

## Бизнес-сценарии

### Регистрация

```text
Команда: RegisterAccount(email, password)
→ Проверка: email нормализован и уникален (set-based, через репозиторий)
→ Событие: AccountRegistered(accountId)
```

- Account создаётся сразу `active` (email-подтверждение отложено, см. открытые вопросы).
- Персональный Workspace здесь НЕ создаётся: Identity не знает слова «workspace». Workspace BC слушает `AccountRegistered` и создаёт персональное пространство сам (своя политика, свой темп, свой сбой не откатывает регистрацию).

### Вход

```text
Команда: SignIn(email, password)
→ Проверки: Account существует и active; password соответствует PasswordHash
→ Событие: SessionCreated(sessionId, accountId)
```

Одинаковый отказ для «нет такого email» и «неверный пароль» — не раскрываем существование аккаунта.

### Продление сессии (rotation)

```text
Команда: RefreshSession(refreshToken)
→ Проверки: Session найдена, active, не истекла, хэш токена совпал
→ Старый refresh token инвалидируется, выдаётся новая пара
→ Событие: SessionRefreshed(sessionId)
```

Rotation обязателен: иначе украденный токен живёт вечно. Повторное использование инвалидированного токена — сигнал компрометации; на этом этапе просто отказываем (детект угона — отложено).

### Выход

```text
Команда: SignOut(sessionId) → Событие: SessionRevoked(sessionId)
```

### Блокировка аккаунта

```text
Команда: BlockAccount(accountId) → Событие: AccountBlocked(accountId)
Политика: на AccountBlocked отозвать все активные сессии аккаунта (SessionRevoked)
```

Отзыв сессий — eventually consistent реакция на событие, а не синхронный обход коллекции: инварианта «ноль активных сессий в той же транзакции» нет, окно в секунды приемлемо.

### Смена пароля

```text
Команда: ChangePassword(accountId, currentPassword, newPassword)
→ Проверка: текущий пароль верный
→ Событие: PasswordChanged(accountId)
Политика: на PasswordChanged отозвать все сессии, кроме инициировавшей
```

## Агрегаты

| Агрегат | Граница согласованности | Почему отдельный |
| --- | --- | --- |
| `Account` | Идентичность, Email, PasswordHash, AccountStatus меняются согласованно | Владелец инвариантов «кто ты» |
| `Session` | Создание, продление, отзыв одной сессии атомарны | См. ниже |

### Почему Session — не коллекция внутри Account

Три вопроса метода:

1. **Инвариант над всей коллекцией?** Нет: «отозвать все сессии» допускает eventual consistency через событие.
2. **Конкурентность:** две вкладки одновременно продлевают разные сессии — не должны конфликтовать на версии Account.
3. **Размер графа:** коллекция сессий растёт бесконечно; грузить её на каждую аутентификацию недопустимо.

Все три ответа против вложения → отдельный Aggregate Root.

## Инварианты

- Email уникален в системе. Это set-based проверка через репозиторий, а не чистый инвариант агрегата — фиксируем честно; гонка двух регистраций на один email дополнительно страхуется уникальным индексом в БД.
- Заблокированный Account не создаёт новых сессий.
- Отозванная или истёкшая Session не продлевается.
- Rotation: использованный refresh token инвалидируется в момент продления.
- Пароль меняется только при предъявлении текущего.

## Value Objects

`AccountId`, `Email`, `PasswordHash`, `AccountStatus`, `SessionId`, `RefreshTokenHash`, `ExpiresAt`.

## Сервисы и порты

- `PasswordHasher` — порт; реализация (bcrypt/argon2) — инфраструктура, в домен не просачивается.
- `TokenGenerator` — порт; выпуск access/refresh пар — инфраструктура.
- Доменных сервисов нет: всё поведение помещается в методы агрегатов и две политики на события.

## События

### Domain events (внутри BC)

`AccountRegistered`, `AccountBlocked`, `PasswordChanged`, `SessionCreated`, `SessionRefreshed`, `SessionRevoked`.

### Integration events (published language наружу)

| Событие | Payload | Основной потребитель |
| --- | --- | --- |
| `AccountRegistered` | `accountId` | Workspace (политика персонального Workspace) |
| `AccountBlocked` | `accountId` | Workspace (деактивация membership — его решение) |
| `PasswordChanged` | `accountId` | пока нет потребителей, публикуем для аудита в будущем |

Принцип минимальности payload: наружу выходит `AccountId` и факт события. Email, display name и прочее не публикуем — если downstream понадобятся атрибуты, это отдельное решение (фасад `getAccountSnapshot` или расширение события).

## Открытые вопросы и предложенные решения

| Вопрос | Решение по умолчанию | Статус |
| --- | --- | --- |
| Подтверждение email | Отложено: нет канала доставки писем в охвате; статус `pending` не вводим, чтобы не тащить полпроцесса | Отложено |
| Восстановление пароля | Отложено по той же причине (нужна email-доставка) | Отложено |
| OAuth / social login | Вне охвата; появление второго способа входа превратит `Credential` в Entity — модель к этому готова | Anti-scope сейчас |
| Где живёт display name / аватар | Предложение: атрибуты Account (имя глобально у человека, как в Asana) | Требует подтверждения |
| Детект угона refresh token (reuse detection → отзыв всех сессий) | Отложено; повторное использование просто отклоняется | Отложено |
| Сроки жизни токенов | Конфигурация deployment, не доменное правило | Решено |
| Что происходит с данными при блокировке | Решение downstream-контекстов (Workspace реагирует на `AccountBlocked`) | Решено границей |

## Что эта итерация изменила в стратегической карте

Ничего — граница Identity подтверждена без сюрпризов. Уточнение одно: `AccountRegistered` становится официальным триггером создания персонального Workspace в Workspace BC (зафиксировать в его итерации).
